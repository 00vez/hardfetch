Protokoll zuletzt aktualisiert: 19.10.2026 (9. Session) — v3.4, Windows und Linux auf einem Renderer

hardfetch – Protokoll & Fortschritt

Projektziel

  • Windows-Konsolentool im Stil von neofetch: kompakte Systeminformationen (OS, Host, Kernel, Uptime, Shell, CPU, Speicher, GPU, Storage) in einem Durchlauf, ohne Logo/Rahmen.
  • C11 für C-Dateien, C++17 nur für WMI/COM-Module; MSVC /MT (statisch), keine externen Laufzeit- oder Bibliotheksabhängigkeiten.

Kontext und Ausgangslage

  • Version 3.4. Ausgangspunkt war 0.2.4 aus August 2025: getrennte Renderer pro Plattform, ein CMake-Target, src/ plus src/posix/.
  • Windows 11 25H2 (26200), Debian 13 unter WSL2, macOS arm64 vorhanden aber in dieser Umgebung ohne Toolchain.
  • Bekannte Einschränkungen aus 0.2.4, inzwischen behoben: AMD-iGPU meldete 0 VRAM, CPU-Temperatur immer N/A, Kernel-Build UBR falsch, RAM-Frequenz fehlte teilweise.
  • Neu und weiterhin offen: Swap wird auf keiner Plattform gezeigt, macOS ist nicht im Release, CI fehlt.

Architektur und Entscheidungen

  • Ein Renderer für beide Plattformen. src/main.c, render.c, fmt.c, edid.c, output.c, debug.c werden von Windows und POSIX gemeinsam gebaut. Das erzwingt gleiche Ausgabe statt nur ähnlicher: Label-Spalte 14, Detailzeilen bei 13, Trenner |, gleiche Einheiten.
  • Collect/Render-Trennung. Jedes Modul liefert *_collect(hf_state*), das Rendern liegt an einer Stelle. Erst dadurch sind -l und -d überhaupt möglich.
  • Statische gegen flüchtige Felder. Statisch einmalig (OS, Board, Shell, RAM-SPD, Disk, Display), flüchtig pro Tick (CPU-Takt, Last, GPU, Uptime, IP). -l sammelt nur die flüchtigen neu.
  • Zwei Threads, nicht mehr. Worker sammelt GPU, Shell, Terminal, Display; Main sammelt den Rest. Das Load-Messfenster überdeckt die Collection, kostet also keine eigene Wartezeit.
  • Windows-Datenquellen: GPU über D3DKMT (gdi32 per LoadLibraryA) statt WMI, NVML-Geräte über PCI-Bus-ID zugeordnet; CPU-Takt über CallNtPowerInformation; CPU-Temperatur über den perflib-Provider in advapi32; Kernel über RtlGetVersion; Display über QueryDisplayConfig mit EDID-Fallback aus dem Registry-Key Enum\DISPLAY.
  • Linux-Datenquellen: GPU über /sys/class/drm plus NVML, RAM-SPD über dmidecode, Temperatur über /sys/class/thermal, beste Schnittstelle über die Default-Route aus /proc/net/route, Version aus VERSION in os-release.
  • Ein EDID-Parser für beide. src/edid.c, am echten Blob des AOC3202 gegen das echte Binary geprüft: 32G2WG8, 698x393 mm, 31,5 Zoll — dieselben Werte, die fastfetch nennt.
  • Apple-Zweige unverändert. apple_pmgr, apple_smc, HID-Fallback bleiben, zielen aber noch auf die alte Kollektorform und sind in dieser Umgebung nicht baubar.

Akzeptanzkriterien

  • Kurzformen -h/-v/-a/-l/-d auf beiden Plattformen identisch verhalten; unbekannte Flags und die entfernten --net/-n ergeben Exit 1 mit Meldung auf stderr.
  • Layout identisch: Label-Spalte 14, Detailzeilen bei 13, Trenner |, gleiche Einheiten. Auf Windows und Linux gegen dieselbe Ausgabe geprüft.
  • Performance: Standardansicht Windows 49 ms gegen 283 ms in 0.2.4; Linux 20 ms. Referenz fastfetch 17 ms. Prozessboden dieser Maschine 3,3 ms.
  • Display liefert Name und Größe auf beiden Plattformen. Windows liest das EDID-Blob aus dem Registry, Linux aus /sys/class/drm/; Parser gegen das echte AOC3202-Blob geprüft, 32G2WG8 / 31,5 Zoll.
  • Kein Feld wird geraten: fehlt eine Quelle, entfällt die Zeile. Auf WSL fehlen deshalb CPU-Temperatur, zweite GPU und Display, weil keine Thermalzone und kein DRM-Konnektor existieren.
  • Beide Builds ohne Warnung; AddressSanitizer sauber über Standardansicht und -a.
  • Release-Binaries tragen SHA-256, die in SHA256SUMS, im scoop-Manifest, in den drei winget-Manifestdateien und der brew-Formel identisch stehen.

Aktueller Status — IST-Stand v3.4

  • Windows: build\Release\hardfetch.exe, MSVC /MT, 0 Warnungen, ASan sauber. Standardansicht 49 ms, -a 230 ms.
  • Linux: build-wsl/hardfetch, gcc, 0 Warnungen. Standardansicht 20 ms, -a 155 ms. Verifiziert auf einer Debian-13-VM, die nur ueber einen Sprung-Host erreichbar ist.
  • Release 3.4 mit beiden Binaries und SHA256SUMS. Heruntergeladen, Pruefsummen bestaetigt, Linux-Binary auf der VM ausgefuehrt.
  • POSIX-Build war seit 3.0 kaputt und wurde es erst auf der Debian-VM, nicht unter Windows entdeckt: output.c hatte die neuen Win32-Aufrufe ohne Guard, die Legacy-Deklarationen lagen in einem #ifdef __cplusplus-Zweig, main.c includierte zwei Header nicht.
  • Swap fehlt auf beiden Plattformen. Linux kann es aus /proc/meminfo, Win32 bietet nur das Commit-Limit. Bewusst nicht ergaenzt, weil die Zeile auf Windows etwas anderes bedeuten wuerde.
  • macOS ist nicht im Release. Die Apple-Zweige zielen auf die alte Kollektorform; hier gibt es keinen Apple-Toolchain.

Offen — noch zu tun

  • macOS auf das v3-Layout portieren. Ohne Apple-Toolchain nicht verifizierbar, deshalb bewusst offen statt behauptet.
  • Swap entscheiden: entweder nur unter Linux als Zeile nach RAM, oder ganz weglassen. Aktuell weggelassen.
  • CPU-CAS-Latenz unter Windows: die meisten Firmwares melden sie nicht, und rohes SMBIOS ist gesperrt. Ohne gangbaren Weg.
  • CI-Matrix (Windows, Ubuntu, macOS) fehlt. Zwei der drei Pfade sind bisher nur manuell geprueft.
  • Schnellster Netzwerkpfad unter Linux: der Resolver der VM haengt zeitweise 5 s. Der Lookup ist heute begrenzt, das Ergebnis faellt dann auf N/A zurueck statt zu blockieren.
  • winget ist ueber winget install 00vez.hardfetch weiterhin nicht installierbar. Ein PR gegen microsoft/winget-pkgs wurde erstellt und auf Wunsch des Nutzers wieder zurueckgezogen, samt Fork. Das Manifest liegt fertig unter packaging/winget/ und kann jederzeit neu eingereicht werden.

Protokoll vom 19.10.2026 (9. Session) — v3.4: ein Renderer, POSIX gefixt, Display auf beiden

Ausgangslage

  • Das Linux-Binary behauptete im Release 3.3 die Version 3.3, verhielt sich aber wie 0.2.4. Statt das in den Release-Notes zu verstecken, wurde der Weg gewaehlt, den POSIX-Kollektoren denselben State fuellen zu lassen wie die Windows und den gemeinsamen Renderer zu benutzen.
  • Referenz fastfetch 2.69.0 auf demselben Rechner: 45 ms Standardansicht, 31 ms Modulboden, 11,5 MB. hardfetch 0.2.4: 283 ms.

Befunde, die erst auf der Debian-VM sichtbar wurden

  • POSIX-Build war seit 3.0 kaputt. Die Behauptung, er kompiliere weiter, war eine Symbolabgleich-Pruefung und kein Build. output.c ist gemeinsam und hatte die Win32-Aufrufe fuer Screen-Clear, Cursor und Tastatur ohne Guard; die Legacy-Deklarationen lagen in einem #ifdef __cplusplus-Zweig; main.c includierte cpu_temp.h und memory_spd.h nicht.
  • -a brauchte 5,2 s bis zum ersten Bild, Standardansicht 20 ms. getaddrinfo und connect hatten kein Timeout und liefen auf dem Main-Thread vor dem Rendern. Der Resolver der VM haengt zeitweise rund 5 s, meistens ist er in 2 ms fertig.
  • RAM-Speed war unter Linux gar nicht implementiert, nur nicht erreichbar. Ein eigener SMBIOS-Parser wurde verworfen, weil sich die Offsets ohne echte Struct-Bytes nicht pruefen liessen; stattdessen dmidecode, wie fastfetch es unter Linux auch nutzt.
  • Thermal- und DRM-GPU-Pfade waren ungetestet, weil WSL weder Thermalzone noch DRM-Karte hat. Beide nehmen ihr sysfs-Wurzelverzeichnis aus einem Makro, das zur Laufzeit nichts aendert, und liessen sich gegen eine Fixture fahren: 47 °C aus der Zone x86_pkg_temp statt acpitz, AMD-iGPU mit 512 MiB.

Fixes in 3.4

  • Public-IP auf eigenem Thread, connect non-blocking mit 1500-ms-poll, Join vor dem ersten Bild begrenzt. 25 Laeufe auf der VM: Maximum 166 ms.
  • disk_volume war char[8], /home/user wurde auf genau 7 Zeichen zu /home/u, statvfs scheiterte, die Disk-Zeile verschwand. Meine erste Erklaerung, es liege an zwei abgeschnittenen Pfadkomponenten, war falsch.
  • Ausgabe ueber ssh nutzte ein nacktes LF. Ein Terminal rueckt eine Zeile runter, ohne die Spalte zurueckzusetzen; ab Spalte 78 verschmolzen Zeilen. Auf Windows nur nachgemessen worden, daher nicht aufgefallen.
  • /proc/cpuinfo steckt den Takt in den Modellnamen, die CPU-Zeile las sich i3-7100T CPU @ 3.40GHz.
  • uptime_collect ohne debug_begin, das Log landete im Host-Modul. Zwei Threads schrieben ungeschuetzt auf stderr und schnitten sich die Zeilen halb. PCI-Vendor 1B36 war als QEMU beschriftet, ist aber Reds QXL.
  • Load sprang zwischen 0 und 100 Prozent: ein 20-ms-Fenster auf zwei vCPUs sind vier Ticks, unter drei ist der Quotient Rauschen. distribution VERSION statt VERSION_ID, damit 13.7 (trixie) statt 13 erscheint.

Zwei Regressionen, die erst die Messung auf der VM zeigte

  • Der Lookup-Thread wurde pthread_detachet und danach gejoint. Ein Join auf einem detach-Thread kehrt sofort zurueck, die Wartezeit fand nie statt.
  • fetch_one wertete das Ende des Response-Bodys als Fehler, weil ein Flag gleichzeitig “Austausch erfolgreich” und “mehr Daten” transportierte. Die Antwort kam korrekt an und wurde trotzdem verworfen.

Messwerte

  • Windows: Standardansicht 49 ms, -a 230 ms, -d 50 ms. Ausgangspunkt 283 ms.
  • Prozessboden dieser Maschine: leeres C-Programm 3,3 ms. Die frueher gemessenen 23 ms waren Overhead der Messmethode, nicht Windows.
  • Linux (Debian 13, 2 vCPUs): Standardansicht 20 ms, -a 155 ms.
  • Beide Builds 0 Warnungen, AddressSanitizer sauber.

Packaging und der winget-Versuch

Protokoll vom 30.08.2026 (6. Session) - macOS Silicon Build-Fehler & Fixes

Fehlerursachen (AppleClang 21.0.0 / macOS SDK)

  • CMakeLists.txt v0.1.0 Windows-only: message(FATAL_ERROR "hardfetch requires Windows") bei Zeile 10, VERSION 0.1.0. Fix: Dateiaustausch mit v0.2.0 POSIX-Branch (else() + src/posix/*.c).
  • HOST_NAME_MAX fehlend: AppleClang liefert es nicht über <limits.h>. Fix: <sys/param.h> + #define HOST_NAME_MAX MAXHOSTNAMELEN in main.c.
  • u_int / u_char / u_short unbekannt: sys/sysctl.h (macOS) erwartet sie, Header liefern nicht. Fix: Typedefs in kernel_posix.c, uptime_posix.c, memory_posix.c.
  • mach_host_t unbekannt: Apple SDK nutzt mach_port_t. Fix: Ersetzen in memory_posix.c.
  • IFF_UP / IFF_LOOPBACK nicht deklariert: net/if.h auf macOS unvollständig. Fix: Fallback-Defines in ip_addr_posix.c.
  • Build-Verifikation: cmake -B build-silicon -S . + cmake --build build-silicon durchlaufen; Binary build-silicon/hardfetch erzeugt.

Vermeidung für Zukunft

  • Vor POSIX-Build immer CMakeLists.txt-Version prüfen (VERSION 0.2.0, else()-Zweig vorhanden).
  • macOS-Defines (HOST_NAME_MAX, u_int-Familie) als ersten Schritt in POSIX-Dateien bereitstellen, nicht pro Fehler nachtragen.
  • Wenn sys/sysctl.h verwendet wird: Typedefs immer vor dem Include einfügen (AppleClang 21).
